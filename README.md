# align-with-me

一个让 Agent 先对齐用户想看到的结果，再开始实现的协作技能。

## 先看一个常见场景

你让 Agent 做一个产品、自动化流程或系统改动。它很快给出架构、代码和测试，结果也许能跑；到了验收环节，你才发现，双方理解的“完成”并不一样。

- 你想验证一个能省时间的最小流程，Agent 交付了一套功能齐全、操作路径很重的系统；
- 你有一个关键前提需要做决定，Agent 直接替你选了方案；
- 需求里的 `X`、结果里的 `Y` 和验收方式 `Z` 没有被说清，返工时才发现起点就偏了；
- 测试证明代码符合预期，却没证明用户能在真实场景里得到想要的结果。

问题的成本在于偏差会被逐层放大。一个起点含糊的需求，经过架构、实现和测试之后，往往会变成一套看起来很完整的答案；改起来，成本也跟着上升。

## 这个技能在解决什么

中心问题只有一个：

> 开始动手前，Agent 和用户是否在说同一件事？

`align-with-me` 把用户可观察的结果放在工作链条两端：

```text
用户意图 → 可观察结果 → 验证方式 → MVP 范围 → 实现 → 用户层验收
```

它要求 Agent 先用一句具体的话重述目标：

> 你希望：当你做 X 时，会看到 Y，并通过 Z 验证。

用户确认后，Agent 再处理假设、范围、架构和代码。这样做的价值很直接：真正会改变结果的歧义，在成本最低时暴露；MVP 先证明闭环；扩展想法有明确位置；交付结果也有用户可以亲自执行的验证方式。

## 它具体缓解哪些痛点

- **目标漂移**：把“做一个功能”落到具体场景、可观察结果和验证方式，减少双方对“完成”的不同理解。
- **范围膨胀**：把能证明目标的最小闭环放进 MVP，性能、扩展性和顺手增加的功能单独放到扩展区。
- **假设藏在实现里**：确认后列出假设；会改变结果或范围的部分交给用户决定，避免 Agent 默默替用户下注。
- **验收与真实使用脱节**：交付时回到用户的操作，说明现在能做什么、会看到什么，以及如何验证。

## 它怎样工作

1. **先对齐意图**：Agent 用“你希望：当你做 X 时，会看到 Y，并通过 Z 验证”重述请求，并等待用户确认。
2. **再公开假设**：确认后展示假设台账；重要歧义升级为用户决策。
3. **拆出 MVP**：计划只保留能证明目标的最小端到端工作，扩展项明确标记为可忽略。
4. **回到用户层交付**：用用户能执行的操作或看到的结果完成验收，而不只报告内部测试通过。

## 适用范围

它适合产品、工作流、自动化和系统变更等需要持续协作的任务。简单事实问答和纯只读分析通常无需走完整流程。

## 一句话安装提示词

复制下面这一句发给 Agent：

> 请将当前仓库根目录的 `SKILL.md` 安装为名为 `align-with-me` 的 Agent 技能，读取 `agents/openai.yaml` 作为界面元数据，并在之后涉及产品、工作流、自动化或系统变更的任务中启用它。

## 如何判断它真的在工作

安装后，给 Agent 一个需要修改产品、流程或系统的请求。合适的第一步应该是重述“你要看到什么、如何验证”，并等待确认；确认后再出现假设台账和 MVP/扩展计划；交付时，你能按照 README 或任务中约定的操作判断结果是否符合预期。
